# Scoped database maintenance handoff

## Interfaces and configuration

`lib/database-management.ts`: `getDatabaseStatus(actor)`, `listOwnedRecords(actor,filter,{limit,cursor})`, `previewMaintenance(actor,request)`, `executeMaintenance(actor,planId,confirmation,idempotencyKey)`. Actor must be an administrator; HTTP additionally uses `withApiPermission` and recent reauthentication/origin validation. `MaintenanceRepository(reader,writerFactory,config,actorStillAdmin?)` allows synthetic injection. Worker rechecks the account through auth repository, not maintenance-role SQL.

GET `/api/admin/database/status`, GET `/api/admin/database/records?limit=50&cursor=<exact-IP>&ip=<exact-IP>&olderThan=<ISO-offset-date>`; POST `/api/admin/database/maintenance/preview` `{operation:'invalidate'|'delete',ips?:string[],olderThan?:ISO,retention?:boolean}`; POST `.../execute` `{planId,confirmation,idempotencyKey}`; POST `.../cancel` `{jobId}`. Mutation origin must equal `APP_ORIGIN`. Execute/cancel require POST `/api/auth/reauth` `{password}` first. Invalid requests 400, permission 401/403, changed/expired/used/recovery 409, unavailable dependencies 503; all responses no-store and redact provider/database errors.

`MAINTENANCE_DATABASE_URL` uses the dedicated role from db-pool; optional capability stays disabled if unconfigured. `MAINTENANCE_OWNERSHIP=ip-intel-owned-v1` is an operator attestation that migration-owned `public.ip_intel_reputation` is exclusively owned. Any inbound FK disables maintenance regardless of attestation. Unknown ownership remains visibly read-only. Shared cache/events never writable.

Bulk delete requires BOTH operator-set `MAINTENANCE_RECOVERY_CHECKPOINT_ID` (3–128 safe identifier characters) and `MAINTENANCE_RECOVERY_VERIFIED_AT` (past ISO timestamp), following a real isolated recovery drill. These are operator assertions, not an automated restore verification service. Do not set them until a usable checkpoint exists. No boolean/path/backup upload accepted from browser. Recovery is an operator runbook procedure. Checkpoint identifiers are not sent to browser.

Migration 003 follows 001/002. Exact group roles aligned with 001: `ip_intel_read`, `ip_intel_reputation`, `ip_intel_auth`, `ip_intel_maintenance`. Grants are conditional on role existence. Maintenance has only allowlisted reputation columns, DELETE on owned reputation, job/plan/policy insertion and restricted updates, and append/select audit. No telemetry/account privileges and no audit UPDATE/DELETE. Reputation revision trigger uses global sequence to detect update and delete/reinsert ABA; writer must retain sequence USAGE grant. No COPY from legacy telemetry into reputation.

Preview performs **zero target/reputation-data mutation**, not zero control-plane writes: it persists a durable immutable plan containing the exact target revisions and expiry. Live verification reads that exact plan back and compares all reputation rows and existing audit rows before/after preview. Execution/failure/cancellation audit remains append-only; shared telemetry is preserved.

## Retention scope and worker

Retention is disabled by default and intentionally **one-run**, not recurring. Preview with `retention:true` requires cutoff and snapshots at most 200 exact current targets. Confirmation queues a durable policy/job with affectedCount=0. Worker: `node --import tsx scripts/maintenance-worker.mjs --max-jobs 10`. It uses scoped env connections, rechecks owned scope, actor permission, checkpoint, fingerprint/versions and ten-minute expiry; exact transaction is all-or-nothing. Policies disable after completion/cancellation/failure. No future matching rows are added. Operator must invoke before expiry; no built-in scheduler. Cancelling queued work commits zero data changes. Multiple workers serialize on plan locks; no decorative partial progress.
